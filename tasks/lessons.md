# Lessons

## "Converting a page" to the redesign = porting the sandbox UI, not just theming it
**Mistake:** For the Apple redesign I made the real dashboard theme-aware (added `useTheme()`, colours flipped) but left its OLD layout/components. The user expected it to look like the lab sandbox (donut rings, 4-bar Living Hours meter, big 40px header, frosted cards, spring buttons) — none of that was there.
**Rule:** Migrating a page means (1) the shared kit must actually contain the new visual design (frosted `Card`, `Ring`, `Pill`, spring `Button`, bigger headers, radii, drop shadows), and (2) the page must be rewritten to mirror the approved sandbox layout, wired to real data. Theming (colour tokens) is necessary but NOT sufficient. Before calling a page "done", diff it visually against its `lab/*` reference — same components, same type sizes, same corners/shadows.

## Never add a hook below an early return — it crashes the page after data loads
**Mistake:** On the rota builder (`generate/page.js`) I added `openDays` (useMemo) and `addBusyCover` (useCallback) just below the existing `if (loading) return <Loading/>` guard. First render (`loading` true) took the early return and skipped those hooks; once the fetch resolved and `loading` went false, they ran — React saw more hooks than the previous render and threw "Application error: a client-side exception has occurred". The whole page went blank in production.
**Rule:** ALL hooks (useState/useMemo/useCallback/useEffect/useRef) must sit ABOVE every conditional `return` in a component, so the hook count is identical on every render. When adding a hook to an existing component, scan for an early `if (loading/error/!data) return` and place the new hook above it. Babel/syntax checks will NOT catch this — it's a runtime Rules-of-Hooks violation. Quick check after editing a page: `grep -n "use(State|Memo|Callback|Effect|Ref)(" file` and confirm no hook line number is greater than the `if (...) return` guard's line.

## A new staff/shift field needs BOTH mapping layers, not just the API route
**Mistake:** Added `prefers_consistent` to `/api/staff` (toClient/toInsert/toUpdate) and thought the field was wired. But the staff page (`dashboard/staff/page.js`) has its OWN `fromApi`/`toApi` transforms between the API shape and the local component shape. Neither carried the field, so `toApi` stripped it from every PUT (DB never updated) and `fromApi` dropped it on load and on the save response — the toggle silently reverted and the solver never saw it.
**Rule:** When adding a Staff/Shift field, wire it in TWO places: (1) the API route's toClient/toInsert/toUpdate, AND (2) the page's own `fromApi`/`toApi` (grep the page for `fromApi`/`toApi` — pages map API rows into a local shape with renamed keys like `contracted`/`max`/`keyholder`). Also check other consumers with their own maps: `staffHelpers.mapStaffForCoverage`, the generate route's solver payload, the mobile app. A field that saves in one screen but reverts in another is the tell-tale sign a mapping layer was missed.
